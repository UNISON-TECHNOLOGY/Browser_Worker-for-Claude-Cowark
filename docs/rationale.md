# 根拠・実例集（必読ではない）

`docs/steps-reference.md` は**規則だけ**を置く正本で、毎タスクの冒頭で必ず Read される。
そこに「なぜその規則があるか」を書くと**全タスクが根拠の散文の代金を払う**ため、
経緯・実例・事故の記録はこのファイルに分離してある（2026-07-27 分離。内容の移動のみ）。

**読むのは、規則の意図を確かめたいとき・規則を変えたいときだけ。** 通常の実行では読まない。

## 環境（Cowork / Claude in Chrome）の実測仕様

**bash とブラウザは別マシン。cloud もローカルも同じ。**
ローカル Cowork は `%APPDATA%\Claude\vm_bundles\claudevm.bundle`（vmlinuz + rootfs.vhdx 9.4GB）
＝ Hyper-V 上の Linux VM で動き、ブラウザは Windows ホスト側の ChromeNativeHost 経由で
実 Chrome を叩く。**VM から `localhost:9222`（CDP）には構造的に到達できない**
（Chrome の CDP は 127.0.0.1 バインド）。cloud とローカルの実質的な差は
「plugin hooks が配線されるか」だけ（escalations E4）。

**Cowork から呼べるブラウザツールは16本。** 出典は拡張 v1.0.81 の
`assets/service-worker.ts-*.js` にあるホワイトリスト（sidepanel-iframe トランスポート）:

```
javascript_tool  read_page  find  form_input  computer  browser_batch
navigate  resize_window  gif_creator  upload_image  get_page_text
tabs_context_mcp  tabs_create_mcp  tabs_close_mcp
read_console_messages  read_network_requests
```

- `shortcuts_execute`（拡張の録画ショートカット）は**このリストに無く弾かれる**。
  加えてコード書き出し不可・アカウント内に閉じるため `knowledge/` に地図を残せない
- `file_upload` は存在しない（正しくは `upload_image`）
- `browser_batch` の制約: 入れ子不可・ホワイトリスト外の子で呼び出し全体を拒否・
  最初のエラーで停止（後続は未実行）・子ごとに結果とスクリーンショットが返る
- `javascript_tool` と `browser_batch` は workflow-gate の matcher 内 →
  **凍結してもゲートが効いたまま速くなる**（Bash 送信はゲート対象外なので、そちらへ逃がすより安全）

## 凍結（G'）の背景 — 2026-07-27 の送出0件事故

ONE CAREER Cloud のスカウト送信を Claude Code 環境から Cowork へ移す際、
`scout_send.js`（CDP 9222 接続・CP1〜5 をコードで内蔵）が動かないため、
**CP をチェックリスト化して手動実施に置き換えた**。「値は同一」と注記されていたが等価ではなかった。

- CP がコードなら監査対象は dry-run 出力（有限・機械照合可能）
- CP がチェックリストになると監査対象が**AI の判断そのもの**になり、指摘が無限に出せる
- 結果: pre-send-verifier が5ラウンド。指摘5件（大学リスト二重化・テンプレ判定矛盾・
  config 死パス・文面表現・補充禁止未明文）は**全て記述の不整合**で、候補者選定の誤りはゼロ
- 2時間半で**送出0件**

**教訓**: 実行手段の移植可否だけを見て、実行場所とゲートの性質の変化を見なかった。
移植不能なのは DOM 操作だけで、判定ロジックは純粋計算なのでそのまま救出できた。

## `requires:`（環境軸の失効）の背景

`scout-cdp-operations.md` は 2026-07-13 作成で内容は**正確**、`last_verified` も新しく
`confidence: high` 相当だった。それでも環境が Cowork に移った瞬間、実行不能かつ
**有害**（移植を誘発する罠）になった。**鮮度メタデータ＝時間軸では検知できない失効**がある。

**丸ごと捨てないことの根拠**: この文書を `_archive/` へ移す寸前、中に
「**送信ボタンは `t === '送信'` の完全一致で拾う。`includes('送信')` だと『送信予約』を
誤クリックする**」という事故防止ルールが含まれていることが判明した。
transport 依存の記述に混じって、手段非依存の重要知識が埋まっている。
救出（DOM 操作の要点・判定順・事故防止ルール）を先に行う。

## 種別（kind）の背景 — 寿命の混在

あるサイトのポリシー正本（25KB）に、セッション別の消費履歴（`log` 相当）と
操作手順（`operation` 相当）が同居し、毎タスクで全量を読んでいた。
さらに操作手順が別ファイルと二重定義になり、**敵対的監査が「記述の不整合」を
無限に指摘できる状態**になっていた。`log` を分離し `operation` を一本化して解消。

## index=ルーターの背景

孤児ファイル禁止（全部リンクせよ）だけでは、ファイルが増えるほど読む量が増え続ける。
実測: あるサイトの20ファイル構成で、スカウト1タスクの読み込みが 61.5KB。
プラグインは自分の部品を `docs/parts/index.md` でルーティングしているのに、
ワークスペースのナレッジには同じ規約が無かった（片手落ち）。

## 必読ファイルの行数上限を機械強制する理由

D-2 に「150行超えたら分割」と明記した当日、同じ規則を書いた本人が
`steps-reference.md` を 151行 → 303行（13.3KB → 26.3KB）にした。
`delve-start.md` も 4.9KB → 9.9KB。全タスクがこの増加を毎回払う構造だった。

原因は**規則の正本に根拠の散文を書いたこと**（1規則あたり3〜6行の「なぜ・いつの事故で」）。
文書のルールでは止まらないと実証されたため、`scripts/lint.py` で行数上限を機械強制する
（「判断はエージェント、強制は機械」— hook 側で確立したのと同じパターン）。

## コンテキスト管理見直し（2026-07-28）の判断

**deny 減衰は「文言のみ可変・判定は不変」**。停止フラグが残っている間、同じ長文 deny を
毎コール再送するとコンテキストが理由文で埋まる（1回で伝わる情報を N 回払う）。そこで同一理由の
3回目以降は1行の短縮版にした。**減衰させるのは文言だけで、deny する条件は一切触らない** —
「うるさいから通す」はゲート緩和であり別物。test-hooks に「連投しても常に deny」を入れて線を固定した。

**正本一元化の対象に hook 出力文言も含む**。money-watch の deny に復帰手順3ステップを書いていたため、
`docs/steps/money-recovery.md` と二重管理になり、どちらが正か分からない状態だった。
**hook はフル手順を埋め込まず「フラグを置いた事実 + 正本パス」だけを返す**（乖離事故の予防と、
毎回払う出力量の削減が同時に効く）。あわせて全 deny に `/状態確認` への導線を1つ足した —
compaction 等で文脈を失っても deny 1回で状態一覧に自走できる（発火仕様は escalations E5 で未確定）。

**非ホットパスにも機械上限を設ける**。ホットパス予算（バイト厳格）の外側は「150行超えたら分割」の
文書ルールしか無く、`command-registry.md` が 160行に育っていたのを人力レビューでしか検知できなかった。
必読ファイルで実証済みのとおり文書のルールでは止まらないので、緩い閾値（150行 WARN / 200行・32KB ERROR）
で機械化する。厳格にしないのは、非ホットパスは1タスクが必ず読むわけではなく肥大の代金が全タスクに乗らないため。

**収束条件はレビュアー自身の定義ファイルに置く**（v1.9.0）。design-critic の「最大2周」は
呼び出し側3箇所（steps-reference Step H / parts/page-improve / parts/ad-to-lp）に分散し、
parts/imagegen では欠落していた。上限を知らないのは審査を止める当事者＝エージェント本体なので、
上限は `agents/design-critic.md`「収束条件」に正本を置き、呼び出し側は1行ポインタに統一する。
（pre-send-verifier の5ラウンド空回りと同型のリスクだった。中間物まで critic に回すと opus の
起動が積み上がるだけで品質は上がらないので、審査スコープの線引きも同じ思想で維持する）

## ローカルファースト化（v1.11.0）の判断

**原則: hook でしか表現されない規律を作らない。** すべての機械ゲートは、(a) 対応する自己規律の
正本と (b) hook に依存しない到達経路の2つを併せ持つこと。

実利用の大半がローカル Cowork（hooks 未配線 = E4）だと確定したことで、hook 前提の設計の穴が
表に出た。`session-rules.txt` は SessionStart 注入だけを到達経路にしていたため、ローカルでは
16項目全部が届かず、特にインジェクション耐性・エスカレーション発火条件・削除ガードは
他ファイルに複製が無く**丸ごと消失**していた（複製禁止の原則と、単一の到達経路の組み合わせが
事故になる）。Money Watch も同様に検知が機械側にしかなく、ローカルでは検知ゼロだった。

対処は「複製する」ではなく「到達経路を増やす」— 正本は1つのまま、delve-start 手順0.5 が
注入の有無を見て自力で Read する。あわせて delve-start の起動理由から「ゲートがブロックするため」
という hook 依存の動機を外した（ブロックされない環境で手順を飛ばす誘因になる。ローカルは
ゲートが発火しないからこそ手順が唯一の防御線）。

検証側は逆向きの事故が起きていた: 実機 deny を PASS 基準にする項目にローカル分岐が無く、
ローカルで full を回すと E4 の既知不発を**新規バグ FAIL として誤報告**する。既知の環境制約は
SKIP(理由) とし、代わりに自己規律が働いたかを見る LV1〜LV3 を置いた（「機械が止めたか」ではなく
「止められない環境で自分が止まれたか」を測る項目が必要だった）。

## その他の実測メモ

- **Money Watch の強/弱分離**: 単独の「決済」「請求」「課金」「お支払い方法」は
  媒体・SNS・広告の管理画面のナビに常在するため、これで停止すると画面を開いた時点で
  定常タスクが毎回詰む（解除に strategy-advisor + ユーザー承認が必要だった）
- **`upload_image` のゲート漏れ**: critic-gate が存在しない `file_upload` を見ていたため、
  artisan の生成画像を無審査で外部サイトへアップロードできる経路が開いていた（v1.3.0 で封鎖）
- **サブエージェントの無駄起動**: Step I が「定常タスクの締め」で outcome-verifier を
  無条件に義務づけていたが、OV Gate hook は `bulk_send` のときだけ発火する。
  読み取りだけのタスクには照合する CP 証跡が無く、渡す材料がないまま起動していた（v1.5.0 で限定）
- **Chrome エンタープライズポリシー**: 拡張は `managed_schema.json`
  （`blockedUrlPatterns` / `forceLoginOrgUUID`）に対応。ブラウザ本体強制のため hooks の
  生死に無関係で、VM 内の AI からは到達不能。ただし粒度は URL 単位のみ・適用は人手の
  レジストリ操作で、**設定者と運用者が同一人物のうちは導入しない**（詳細は escalations.md）
