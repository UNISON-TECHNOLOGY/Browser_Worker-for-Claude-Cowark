# Delvework ステップ正本（A〜K リファレンス）

> ブラウザ変更操作タスクの手順の正本。/タスク開始（procedures/delve-start.md）はフラグ操作の最短経路のみを書き、
> 方法論の本体はここに一元化する（各手順書はここへのポインタのみ。複製は乖離事故のもと）。

## ステップ一覧

| Step | Code | 名称 | 要点 |
|------|------|------|------|
| A | Order | タスク指令 | パラメータ確定・破壊的操作の有無を判定 |
| B | Recon | 外部探索 | ナレッジ・過去ログを読み、フェーズ判定（B-4） |
| C | Probe | 内部探索 | ブラウザでページ構造を取得、ナレッジと照合 |
| D | Map | マッピング | 構造をナレッジに記録（下記 D-2） |
| E | Observe | モニタリング | 変更前状態の記録 + CP証跡定義（下記 E-3） |
| J | Report | 差分比較 | フェーズ②③④のみ、E直後。前回 after_state と今回 before_state を比較し、外部変更/リセットを検出したらユーザーに報告 |
| F | Plan | プランニング | 実行計画 + レギュレーション検証（下記 F-4）。**計画に不可逆な一括送出（スカウト/投稿/配信/入稿）が含まれるなら `touch memory/.workflow/bulk_send` を宣言**（以後 psv_done まで変更操作が hook でブロックされる） |
| G | Act | アクション | 実行。生成物があれば H に遷移。**フェーズ④で手順が固定したら凍結スクリプト経由に移す（下記 G'）** — 1操作ごとの LLM 往復が消え、ローカル環境ではこれが主経路 |
| H | Review | レビュー | 生成物・破壊的操作のユーザー承認（無人運用時は docs/unattended-ops.md の承認キューに従う）。**一括送信・投稿・入稿など不可逆送出は、承認提示の前に pre-send-verifier サブエージェントの敵対的監査（VERDICT）を材料として添え、監査とユーザー承認が揃ったら `touch memory/.workflow/psv_done`**（bulk_send 宣言済みタスクは psv_done まで hook が変更操作をブロック）。**監査は「実際に送る対象が確定した1回」だけ行う** — 計画段階と選定後の2回に分けない。監査に渡すのは判断の説明ではなく**確定した対象の表**（識別番号・属性・使用テンプレ・添付先）。監査は最大2周で、2周目は1周目の BLOCKER の差分だけを見る（agents/pre-send-verifier.md「収束条件」）。**design-artisan のビジュアル生成物のうち、ユーザーに渡す最終成果物は必ず design-critic の審査を経てから承認に出す（critic を呼ばず直接ユーザーに引き渡すのは禁止 — Critic Gate hook が送付出口で強制）**。**中間物は対象外**: 作業確認用のスクリーンショット・検証中のダミー画像・自分で見るだけの試作は critic を呼ばない（Critic Gate の対象スコープと同じ線引き。中間物まで審査すると opus の起動が積み上がるだけで品質は上がらない）。フラグ運用: artisan へ委譲した直後に `echo "<レビュー対象のファイル名またはパターン>" > memory/.workflow/critic_pending && rm -f memory/.workflow/critic_pass`（**対象を書くこと** — 空にすると全ビジュアル成果物がゲート対象になり、デバッグ用スクショなど無関係なファイルまで送付できなくなる）、critic が PASS を返したら `rm memory/.workflow/critic_pending` して PASS の1行要約を `memory/.workflow/critic_pass` に書き込む。REVISE が返ったら、メインループが FIX 内容を design-artisan に再投入し PASS まで反復（最大2周）してから承認に出す。見た目ものの成果物は、承認の選択肢として「Claude Design ハンドオフ（docs/parts/design-handoff.md）」も提示してよい。ハンドオフしたら成果物の最終正本は回収後のファイルとする |
| I | Verify | チェック | CP証跡照合（I-1.5）+ ログ記録（下記 I-3）+ ナレッジ更新。**不可逆操作があったタスクに限り**（件数は問わない）**outcome-verifier**（送信後検証）に after_state と CP 証跡を渡して独立検証させ、判定要約を `memory/.workflow/ov_done` に書き込む（OV Gate hook: bulk_send 宣言タスクは ov_done なしで k_done 不可）。**読み取りだけで終わったタスク（巡回・状況確認・調査）では起動しない** — 照合する CP 証跡が存在せず、渡す材料がない。締めは main ループが行う。効果測定（返信率・エンゲージ集計）で呼ぶのは別用途で、そちらは件数や期間があるときだけ |
| K | Offer | オファー | 完了報告 → session-log 更新 → k_done |

## 認証フィールドの取り扱い（全ステップ共通・自己規律）

Credential Guard（hook）はペイロード内のキーワードで検知するため、**参照ID（ref）だけを指定した入力はすり抜けうる**（2026-07-24 実測: ref 経由で password 欄への入力が素通りした）。hook は最後の網であって主防御ではない — 以下を自己規律として守る:

- ログイン・認証画面では **autofill の起動（クリックのみ）以外の入力操作をしない**。ref 指定の form_input/type も禁止（ref の先が password 欄かどうかは入力前に要素の type/autocomplete 属性を read_page で確認しない限り分からない）
- 入力先が不明な ref に対する入力は、直前の read_page で要素種別を確認してから行う（type=password / autocomplete=current-password・one-time-code の要素なら入力せず人間に委譲）

## フェーズ判定（B-4）と③構造変更

| # | フェーズ | 条件 |
|---|---------|------|
| ① | 初回 (First Delve) | サイトナレッジなし。**探索は「一番難しい業務ページ」（複雑なフォーム・動的画面）から行う** — 綺麗なトップページでの成功は当てにならず、本番業務の画面で崩れる（外部実務知見） |
| ② | 再訪問 (Return) | ナレッジあり、成功ログなし |
| ③ | 構造変更 (Remap) | **探索中に構造差異検出**（ナレッジの ref/導線が実ページと不一致） |
| ④ | 最適化 (Optimize) | 成功ログ + shortcut_memo あり |

**フェーズ③発動時（実行中いつでも）**: ナレッジと実ページの構造差異を検出したら、古い ref で操作を続けず
`rm -f memory/.workflow/e_done` して Step E（変更前記録）からやり直し、`echo "3" > memory/.workflow/phase` に更新、
D（マッピング）で差異箇所のナレッジを修正してから再開する。

フェーズ④は過去ログの `shortcut_memo` をレシピとして使う。レシピのステップが失敗・不一致になったら残りを破棄し、**自動でフェーズ③（Remap）へ**（下記「フェーズ④の機械検証」と同一挙動。②で続行しない）。

### フェーズ④の機械検証（アクション・キャッシング — 2026-07-23 外部調査で導入）

shortcut_memo は「操作 + 期待ランドマーク」の対で書く（例: `スカウト画面へ /scout 直遷移 @ 見出し「候補者一覧」+ 送信ボタンあり`）。再生時のルール:

1. 各ステップの**実行前**に snapshot でランドマーク（見出し・ボタン名・URLパターン）を照合
2. **一致** → そのまま実行（探索・再マッピングの判断を省略 = 2回目以降は決定的に速くなる）
3. **不一致** → 主観で続行せず**自動でフェーズ③（Remap）へ**（e_done 削除 → E からやり直し。Remap 発動を人の判断に依存させない）
4. ランドマークの無い旧形式 memo はフェーズ②相当として扱う（照合できないレシピを盲信しない）

## G'. 手順の凍結

フェーズ④の次段。1要素ごとの LLM 往復を消す。**凍結手段は `javascript_tool`（ページ内JS）と
`browser_batch`（束ね）の2つだけ** — Playwright / CDP(9222) は Cowork に存在しない。
**既存の Playwright/CDP 資産を「移植」しようとしないこと**（使えるツール16本の一覧・
batch の制約・移植を試みた事故の記録は docs/rationale.md）。

凍結先は2つに分ける（bash とブラウザは別マシン。delve-start 0.5）:

| | 置き場所 | 実行 | 中身 |
|---|---|---|---|
| DOM 側 | `knowledge/sites/<site>/snippets/<用途>.js` | `javascript_tool` | 一括抽出（→JSON）・一括入力・一括操作 |
| 判定側 | `scripts/<タスク名>.js` または手順内の計算 | サンドボックスの bash | 適合判定・許可リスト照合・重複除外・上限管理 |

**判定側は純粋計算なので他環境からそのまま救出できる。移植不能なのは DOM 側だけ**（丸ごと捨てない）。

**凍結の条件**（全て満たす）: フェーズ④到達 / **直近2回以上同じ手順で成功** / ランドマークが安定。

**作り方**:

1. **読み取りから凍結する** — 一覧の全項目を1コールで JSON 化（N回の read_page が1回になる。ここが最も効く）
2. 抽出 JSON を判定側に通し**対象リストを表で出す** = dry-run 出力 = Step H の監査入力
3. **ミューテーションは既定で起こさない**（明示の実行指示があったときだけ）
4. **ゲートを判定側に内蔵**（CP=E-3 / 上限 / 履歴突合 / F-4）。DOM 側は承認済みリストを実行するだけ
5. 送信・保存は1件ずつ、または batch でも**CP5 を1件ずつ確認できる形**にする
6. dry-run 1回・実行1回を実機検証してログに記録し、サイトナレッジに凍結済みと1行書く

**凍結後**: Step E / I / J とユーザー提示・承認は従来どおり省略しない。
セレクタ不一致で落ちたら**フェーズ③へ戻る**（勘で直さず再マッピングしてから凍結し直す）。

## E-3. Critical Point 証跡定義（不可逆操作の前に必須）

変更前記録は**必ずテキスト読取（read_page / browser_snapshot）を含める** — スクリーンショットのみは不可（Money Watch は読取テキストに反応するため、スクショだけで進むと金銭・契約画面の検知面を素通りする）。

操作前に **CP（不可逆操作・品質ゲート・誤操作リスクのある分岐）** を列挙し、各 CP に「**何が見えたら成功と断定するか**」を宣言する:

```
CP = { id, desc(確認すべきこと), proof(ログ行 or スクショパス), on_fail(必ず「判定を緩めず停止/スキップ」) }
```

- 不可逆操作（送信・投稿・公開・削除・保存）の直前には必ず CP を1つ以上置く
- 証跡は **機械検証できるログ行** を第一とする。**証跡が取れない CP は「成功」と記録してはいけない**
- 例: 「送信ボタンを押した」ではなく「完了トーストが出た/残数が減った」を成功条件にする（操作の実行 ≠ 成功）
- **公開系操作（投稿・記事公開・イベント公開等）の CP には「公開後の実体確認」を含める**: 投稿URL・公開ページURLを控えてログに残し、可能なら新規アクセスで実在を確認する（トーストのみでは outcome-verifier の独立検証が VERIFIED にできない — 2026-07-24 実測で Threads がトーストのみのため 2/3 判定になった教訓）

## F-4. レギュレーション検証（全フェーズ）

実行計画の値を運用規則と照合する。規則の在り処（優先順）: タスクYAMLの `regulations` 指定 → `knowledge/data/*-master.md` → サイトナレッジの「レギュレーション」節。無ければスキップ。
違反検出時: 自動修正可能なら修正して通知、不可ならユーザーに判断を仰ぐ。

## D-2. ナレッジ構造記録（消費者で分離する）

```
knowledge/sites/<site名>/
├── index.md          ← ハブ（必須）: 概要・ナビ・探索状況・他ファイルへのリンク
├── <page-a>.md       ← ページ単位のフォーム構造・遷移・要注意要素（英語ケバブケース）
├── *-templates.md    ← 構造・メタデータ（ダッシュボード/分析用）
└── creatives.md      ← 本文全文（生成タスクの参照素材）
```

- **同じ対象でも消費者が違えばファイルを分ける**（構造メタデータ ↔ 本文全文 ↔ 操作手順）
- 150行超えたら分割を検討。分割は**内容の移動のみ**（要約・省略しない — 転記漏れ＝ナレッジ消失。分割前後で総内容が同一であること）。index.md からのリンクを必ず張る（孤児ファイル禁止）
- 生成対象になりうるコンテンツは探索時に**全文**を取得して creatives.md へ（メタデータだけでは改善作業ができない）

### 種別（kind）— 寿命が違うものを混ぜない

| kind | 中身 | ホットパス |
|---|---|---|
| `policy` | 判断基準・条件・ルール | 読む |
| `operation` | 操作手順・セレクタ・落とし穴（環境で失効しうる → `requires:`） | 読む |
| `log` | 実績・消費履歴・セッション記録 | **読まない**（振り返り専用） |
| `data` | 機械照合用の値（送信済みID・マスタ） | 必要な範囲だけ |

寿命の違うものを1ファイルに混ぜない（混在が招いた事故は docs/rationale.md）。

### 有効条件（`requires:`）— 環境軸の失効

`kind: operation` のファイル冒頭に、前提とする能力を宣言する:

```yaml
---
kind: operation
requires: [claude-in-chrome]   # 例: playwright / cdp-9222 / bash / python3 / ffmpeg
---                            #     sqlite / design-sync / slack / local-schedule
```

書くのは「セッション開始時に有無を判定できる能力」。照合は delve-start 0.5 で行う:

- **満たさないファイルは読まない・従わない・他手段へ「移植」しない**。代替手段を自分で探さず、
  実行できない旨と足りないものを報告して指示を仰ぐ
- 恒久的に満たせなくなったら `_archive/` へ移すが、**手段非依存の知識**（セレクタ・判定順・
  事故防止ルール）を先に現行ファイルへ救出する。**丸ごと捨てない**

### index はハブであると同時に**ルーター**

孤児ファイル禁止だけだと、ファイルが増えるほど読む量が増え続ける。
index.md 冒頭に**タスク別・読むファイル表**を必ず置き「これだけ読めばよい」を明示する
（`_archive/` と `logs/` は読まない旨も書く）。新規ファイルはルーター表のどの行で読むかまで決め、
どの行にも入らないなら必要か疑う。I（ナレッジ更新）でファイルを増減したら表も同時に更新する。

### 鮮度メタデータ（staleness 管理）

index.md の冒頭に YAML フロントマターで記録し、D（マッピング）・I（ナレッジ更新）のたびに更新する:

```yaml
---
last_verified: 2026-07-23   # 実ページと照合できた最終日
verify_count: 5             # 照合成功の累計（多いほど信頼できる地図）
confidence: high            # high / medium / low（直近で phase3 が出たら low に落とす）
---
```

**更新条件**: last_verified / verify_count を更新できるのは**全体構造の確認を伴った場合のみ**（フェーズ①②③の D / I）。フェーズ④のランドマーク照合は部分確認なので更新しない（部分照合で high の地図が延命するのを防ぐ）。

**陳腐化ポリシー**: B-4 でナレッジを読むとき、last_verified が30日超過 or confidence: low なら、フェーズ④条件を満たしていても**フェーズ②（照合しながら実行）に落とす**。古い地図を信じて突き進まない。

**失効の2軸（まとめ）** — B-4 では両方を見る:

| 軸 | 判定 | 該当したら |
|---|---|---|
| **時間**（鮮度メタデータ） | last_verified 30日超 / confidence: low | フェーズ②に降格して照合しながら実行 |
| **環境**（`requires:`） | 現環境が要求能力を満たさない | **そのファイルを読まない**（降格ではなく除外。移植もしない） |

## I-1.5. CP証跡照合

E-3 で定義した各 CP について実際の証跡を照合。取得できなかった/条件を満たさない操作は「成功」と記録しない。
CP 不合格でスキップした対象は理由（どの CP がなぜ落ちたか）をログに残す。

## I-3. タスク実行ログ記録（必須スキーマ）

`knowledge/logs/<タスク名>_<YYYY-MM-DD>_<HHmm>.md` に **YAML フロントマター付き**で記録する。
フロントマターは B-4 フェーズ判定・ダッシュボードが機械的に読むため省略禁止:

```yaml
---
task: <タスク名>
site: <サイトキー>
phase: 2            # 1:初回 / 2:再訪問 / 3:構造変更 / 4:最適化
status: success     # success / failed / partial / aborted
started_at: "YYYY-MM-DDTHH:MM:00"
finished_at: "YYYY-MM-DDTHH:MM:00"
steps_completed: [A, B, E, F, G, I, K]
errors: []
before_state: { <E で記録した主要値> }
after_state: { <I で確認した主要値> }
shortcut_memo:      # 次回フェーズ④判定・レシピに使う。無ければ []
  - "<効率ルートのヒント>"
---
```

本文は自由記述: 実行内容 / 変更前→変更後 / 学び / エラー。

## I-5. 最短ルート記録

UIより速いパターン（API直接取得・evaluate一括・URL直接遷移）を発見したら、ログの `shortcut_memo` と
サイトナレッジの両方に記録する（ログだけ = 地図に道を描かずメモだけ残すのと同じ）。
**API直接取得は採用前に利用規約を確認**し、初回はユーザーに可否を確認してから。確認結果をナレッジに記録する。

## K. 完了（順序厳守）

1. 完了報告（成功/失敗、Before→After、フェーズ、次回の最適化候補）
2. **先に** `memory/session-log.md` を更新
3. `touch memory/.workflow/k_done`（Log Gate = 運用ルール: session-log を更新するまで k_done を作らない。hook の技術的強制はない — 順序は自己規律で守る）

## エラー処理

スクリーンショットを撮り、状況をユーザーに報告して指示を仰ぐ。**自動リカバリーは行わない**。エラー内容はログに記録する。

## Money Watch 停止からの復帰

タスク中に money_alert（金銭・契約系画面の検知）が立ったら: strategy-advisor に状況を渡して助言（STOP/RESPOND/MONITOR）を得る →
操作内容をユーザーに提示して明示承認 → 承認を得た場合のみ `rm memory/.workflow/money_alert` し、承認の事実を session-log に1行記録して再開。

停止中も**画面を読むこと自体は許可されている**（read_page / get_page_text / computer の screenshot・scroll）。
状況を読めないと復帰手順そのものが実行できないため、意図的にそう設計してある。止まるのは変更操作だけ。
ただし **`browser_batch` は読み取りのみでも停止中は deny される**（既知の不整合 — 同じ読み取りが
包み方で通ったり止まったりする）。停止中は batch を使わず、read_page 等を単体で呼ぶこと。
